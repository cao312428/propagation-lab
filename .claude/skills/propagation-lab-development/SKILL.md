\# 传播实验室开发规范



你正在维护《传播实验室》项目。



这是一个面向数字内容创作者的关键信息传播压力测试工具。



本项目当前技术栈：



\- Vite

\- React

\- TypeScript

\- React Konva

\- HTML Canvas

\- 原生 CSS

\- Vitest



核心目标不是评价作品“好不好看”，而是检测用户主动标记的重要信息在传播过程中是否发生裁剪、遮挡或功能失效。



\## 一、开发总原则



每次只完成用户当前明确要求的一个阶段。



不要因为正在修改某个功能而顺便增加其他功能。



已经通过测试和人工验收的模块，应尽量保持稳定。



在没有明确必要性的情况下：

\- 不进行大规模重构

\- 不更换技术栈

\- 不引入大型 UI 框架

\- 不修改已经稳定的核心算法

\- 不增加未经要求的功能



发现 bug 时，先修复 bug，再继续开发。



\## 二、现有产品边界



本项目不是：



\- AI 美学评分工具

\- 普通聊天机器人

\- 社交媒体发布工具

\- 真实平台官方模拟器

\- 传播效果预测系统



不要添加没有实验依据的：



\- 综合传播评分

\- 安全评分

\- 美观评分

\- 成功概率

\- 注意力预测

\- 获奖概率

\- 用户阅读概率



\## 三、标注坐标规则



所有 annotation 必须永久保存为：



原始图片坐标。



禁止把屏幕显示坐标、CSS 坐标或缩放后的 Konva 坐标作为最终数据保存。



浏览器窗口尺寸变化、图片显示尺寸变化、1:1 / 9:16 模式切换时，都不得改变 annotation 的原图坐标。



涉及坐标计算时：



1\. 明确原图坐标系

2\. 明确裁剪坐标系

3\. 明确显示坐标系

4\. 不要混用 CSS width/height 与 Canvas 内部 width/height



\## 四、几何可见率规则



当前几何分类规则：



\- visibleRatio >= 0.85 → 完整

\- 0.50 <= visibleRatio < 0.85 → 部分可见

\- visibleRatio < 0.50 → 严重缺失



这是当前产品规则，不是行业标准。



几何可见率只表示标注区域经过裁剪和遮挡后剩余的面积比例。



永远不要把几何可见率描述为：



\- 文字可读率

\- 用户注意力

\- 信息理解率

\- 扫码成功概率

\- 传播成功率



界面中应持续保持类似说明：



“几何可见率不代表区域内的文字能够被准确阅读。”



\## 五、裁剪规则



当前支持：



\- 1:1 居中裁剪

\- 9:16 居中裁剪



图片不得被拉伸。



裁剪必须通过真实几何区域计算。



不要为了增加功能数量自行加入新的比例。



\## 六、通用界面遮挡



通用界面遮挡是压力测试使用的简化模型。



当前参数属于项目内部测试规则，不代表任何真实平台的官方界面尺寸。



不得将其描述为：



\- 抖音官方安全区

\- 小红书官方安全区

\- Instagram 官方安全区

\- 任何具体平台官方标准



遮挡计算必须避免重叠面积被重复扣除。



\## 七、二维码检测



二维码必须通过真实像素解码判断。



不能根据几何可见率推测二维码是否可以扫描。



二维码检测应满足：



\- 使用原图有效像素

\- 使用离屏 Canvas 或独立计算流程

\- 不依赖浏览器预览尺寸

\- 不依赖 CropPreview 的缩略图尺寸

\- 不因 CSS 缩放改变识别结果

\- baseline 与 current scene 使用一致的 ROI/padding 逻辑



重要不变量：



如果一个有效二维码：

\- 几何保留 100%

\- 没有遮挡

\- 没有主动进行画质退化



那么 baseline 和 current scene 应得到一致的解码结果。



如果这一条件不成立，应优先视为实现 bug，而不是传播风险。



二维码识别成功也不能表述为：



“所有设备一定可以扫描。”



\## 八、问题诊断



诊断只能基于已有几何数据生成。



可以判断：



\- 无明显问题

\- 主要受裁剪影响

\- 主要受界面遮挡影响

\- 同时受裁剪和界面遮挡影响



可以根据几何关系给出：



\- 向中央移动

\- 向左/右移动

\- 向上/下移动

\- 避开界面遮挡区域

\- 缩小或重新布置信息区域



不要生成美学建议。



不要评价用户设计质量。



\## 九、版本对比



修改前与修改后的对比是：



设计 → 测试 → 修改 → 再验证



当前区域匹配规则为：



标签类型 + 同类型标注顺序。



不要描述为自动语义匹配或视觉元素识别。



百分比变化应使用“百分点”。



例如：



54.7% → 92.0%

应描述为：



“增加 37.3 个百分点”



不要描述为：



“提高 37.3%”。



如果修改前后测试场景不同，不应生成直接比较结论。



\## 十、报告



报告必须复用已有检测结果。



不要在报告模块重新实现第二套几何判断算法。



报告可以汇总：



\- 测试场景

\- 标注数量

\- 完整 / 部分可见 / 严重缺失

\- 裁剪保留率

\- 最终几何可见率

\- 问题来源

\- 受损方向

\- 修改建议

\- 二维码解码结果



不要生成未经验证的综合分数。



\## 十一、代码结构



计算逻辑与 React UI 分离。



优先将纯计算放在：



src/utils/



类型定义放在：



src/types.ts

或已有的 types 文件中。



组件放在：



src/components/



React 组件主要处理：



\- 状态

\- 交互

\- 展示



不要把几何算法、二维码像素处理和大量业务规则全部塞进 App.tsx。



能写成纯函数的逻辑优先写成纯函数，以便单元测试。



\## 十二、修改代码前



开始任务前：



1\. 阅读与任务相关的现有代码

2\. 阅读现有测试

3\. 确认功能是否已经存在

4\. 避免重复实现

5\. 判断这次任务是否会影响核心算法



如果用户要求只是 UI 优化：



不要修改检测算法。



如果用户要求只是修复 bug：



不要顺便增加功能。
